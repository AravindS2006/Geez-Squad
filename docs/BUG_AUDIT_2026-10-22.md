# Geez Squad bug audit — 22 October 2026

This audit covers account entry, member-to-account linking, studio operations, financial writes, live participation, conference lifecycle, data export, diagnostics and deployment readiness. Passing automated checks is not a claim that all possible defects are eliminated.

| P1 | Request IDs were discarded; non-JSON failures broke error handling | Typed client errors, correlation headers, visible support references |
| P1 | Error logs lacked route/operation context | Structured, level-filtered, allowlisted logs across API/auth/email boundaries and server rendering |

## Verification

Initial baseline: 338 unit tests and TypeScript passed despite the issues above. New regression coverage exercises account-link ownership, verification gates, delayed signup, acceptance retries, contact edits, decline/resend/withdraw, term selection, logger redaction, client error parsing, SMTP failures and independent device setup. Current verification: 357 unit tests, TypeScript, 179 authentication/access API checks, 68 studio-operation API checks, and all 47 browser tests passed. Browser coverage includes automated accessibility, 320/390px authentication, persisted onboarding, studio CRUD, galleries up to 48 trainees, camera recovery, live controls and historical saves. An eight-member concurrent HTTP rehearsal completed 51 requests with zero failures; it does not measure WAN or WebRTC capacity. The optimized Next.js production build passed.

PostgreSQL migration rehearsal passed in an isolated temporary schema, preserving legacy credentials/sessions and checking stable-link uniqueness, account-deletion history retention and cascade behaviour. No real user data was copied into rehearsal fixtures. Isolated email-mode checks also passed: 28 testing-signup checks and 9 deferred-email checks.

## Practical limits

- Gmail is a free, quota-limited sender. Successful SMTP acceptance does not guarantee inbox placement; actual verification and recovery delivery must be tested.
- Live expiry enforcement depends on polling/actions and available room services. It is not an instantaneous scheduler.
- Existing clients with no valid term must be assigned real membership dates before participation; backfill never invents payments or terms.
- Studio operation reads still load historical rows as a batch. Pagination remains a future scaling improvement.
- This phase does not add paid billing enforcement, staff login permissions, payroll, GST invoicing or automatic renewals.

## Production impact before migration

Read-only assessment: 5 accepted coaching clients, 3 existing physical member records, 2 unambiguous links, 3 new member records required, zero conflicts, 3 clients without active terms, and 5 sessions marked live. Enabling the selected access policy will prevent those 3 clients from participating until a real membership is assigned. No terms or payments were fabricated.

After explicit release approval, the additive production migration and backfill passed. Preservation checks confirmed existing accounts, password hashes, user profiles and roles were unchanged. A second preflight found all 5 clients already linked, zero remaining records to create/link, zero conflicts and 3 clients still requiring valid terms.

The staged production build passed with the configured Gmail sender. Four real SMTP sends succeeded with no delivery failures; the controlled mailbox owner confirmed receipt of verification and recovery email and opened all verification links. Both disposable accounts were verified through those links. Twenty-nine staged production checks passed across both roles, sign-in again, member-plus-term assignment, acceptance, LiveKit room creation and token eligibility, pause/revocation, room closure and retained history. Test tokens/passwords were not logged. This verifies room-service and access boundaries; a two-device WAN media call remains a manual rollout check.

Initial GitHub CI passed both API suites and 46 browser cases; one worker-script interception hit a transient ECONNRESET. The harness now uses Playwright's bounded network retry without retrying HTTP errors or weakening recovery assertions. A subsequent run exposed a GPU-initialization fixture that assumed CPU Heavy inference would always be fast enough to avoid adaptation on hosted hardware. That fixture now isolates initialization with deterministic reported timing; the three separate slow-inference cases retain their adaptation assertions. The final full CI run is required before promotion.

Additional protected-stage browser verification passed at 320/390/1440px with zero automated accessibility violations. Two real cloud participants received decoded synthetic remote video; microphone setup, leave/rejoin, roster cleanup, live membership-pause removal and retained history passed, with zero browser runtime exceptions. Disposable rooms/accounts and scoped test studio records were removed. A runtime scan found zero server errors, 5xx responses or revocation failures.
